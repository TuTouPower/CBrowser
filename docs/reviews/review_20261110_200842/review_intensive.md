## 总裁决

这批 181 个提交整体是「多轮审阅驱动的修复 + 四个新功能（LAN 访问、预览缩略图、Profile 编号/分组、设计系统）」的叠加，**主干机制的工程质量是扎实的**：经逐项核实为真的核心修复包括 BEGIN IMMEDIATE 写路径全覆盖、Origin 归一化与 CSRF 双检、网络事务的 DB 内核（四元组 fence、commit 三值校验、重放幂等）、显示编号的事务内分配、字体集隔离骨架、Supervisor 恢复的双 fence 前置、部署链比较与 Python 侧原子写四要素——这些都不是表面功夫，配套测试多数是真行为断言。

**主要风险面集中在三处**：

1. **跨进程状态一致性明显弱于进程内**。网络域是最典型的样本：publication 回执全在 Gateway 内存、ACK 不幂等、revoke 无身份校验、fencing 状态只在 Supervisor 内存且靠 header 自觉携带、已应用状态的运行时读者不做完整性校验、部署指纹哈希的是生成器源码而非产物。单进程内每一段都写得严谨，但崩溃、重启、回执丢失、并发交叠这四种跨进程情形下，API/Gateway/Supervisor/磁盘四方状态没有一个统一的收敛证明。LAN 媒体面还有一整条未接线链（第 50–53 项）：读 applied 配置的函数零调用、allow_lan_media 恒 False、新 stream 与稳态替换都回落 loopback——t042 的 LAN 功能在信令面成立、在媒体面只成立于「apply 当时已存在的 stream」。
2. **多处「声称强度 > 实现强度」的落差**，且多发生在刚被前一轮审阅点名修过的区域：pixel-verified 在生产链路不存在（第 99 项）、A4 限流来源识别在生产部署未接线（第 41 项）、恢复 fencing 防不住在途越过与进程重启（第 48 项）、隐私门禁在 HEAD 实际为红且豁免粒度是整文件（第 128、129 项）、WCAG AA 与「五镜像统一排除 pycache」均无门禁背书（第 105、115 项）。这类落差比单点 bug 更值得警惕：它们会让后续工作基于错误的安全感做决策（p068 把未证实机制写成已定位根因是同一种模式在文档侧的发作）。
3. **门禁体系自身有跨会话破坏与假绿通道**：静态前缀清理会删同机另一会话在跑的容器（第 120 项，与 p051 同源而归因未覆盖）、共享 venv 无锁（第 119 项）、停止断言被探针归一削弱（第 121 项）、普通套件无用例数下限（第 122 项）。在一个以多 worktree 并行跑门禁为常态的工作流里，这三项是会反复咬人的基础设施债。

其余问题多为边沿与一致性缺陷（双份实现、分类口径分歧、死参数、注释与实现矛盾、handoff 过期），单项影响有限，但数量说明这批高速合入（6 天 181 个提交、含多轮全量修复批）后的**一致性收尾没跟上**：同一概念在两层/两进程/前后端各有一份实现或口径的模式反复出现（client_ip 双副本、LAN IP 双校验、limits 与分类三分的前后端分歧、原子写双标准、v2 残留）。
