# bundle_global_strategy

## Summary

The core technical bet is coherent: replacing upstream CloakBrowser-Manager's single-process VNC-era design with per-profile Docker container isolation plus Selkies WebRTC genuinely serves this product's stated purpose (multi-identity/privacy-isolated browser management), and the v2 core that exists is well-engineered (cross-unit evidence: fencing, idempotent journal, fail-closed network policy, real Docker E2E chains). The strategy problem is twofold and mostly about fit and sequencing rather than direction. First, fit: the architecture is sized like a multi-host streaming service — five resident services (Caddy, API, Supervisor, Gateway, coturn), per-profile container pairs, TURN REST credential rotation on a 12h cycle, ICE generation takeover — while every recorded statement of actual use describes a single-user, single-machine, same-host-Chrome deployment (AGENTS.md: '单机 Docker 管理系统'; t009 runs on the owner's Mac/OrbStack). The capabilities that would justify the distributed-systems cost are precisely the ones already waived by user decision (public NAT traversal and native-x86 validation are NOT_RUN/USER_WAIVED), and on 2026-11-02 the acceptance bar for what remains was lowered from 1000-run automated input/clipboard pressure to a manual checklist. The project is paying multi-host engineering prices for a local tool's requirements, and the plan documents have not been re-baselined to admit it. Second, sequencing: the entire closing chain of the v2 plan — t009 acceptance, t010 data migration, t011 legacy removal, t012 formal Docker release — sits in backlog, untouched, while effort continues to flow into the v2 core (docs/ is 5.4MB against src/ at 2.2MB). The repo_template toolchain present in-tree (≈27.7k lines of scripts+tests) is not part of that effort allocation: follow-up q_strategy_02 confirmed it is a platform artifact authored in an external template repo, imported wholesale in a single commit and never edited in this repo's history, so f_global_strategy_03 was adjusted to a consumption-risk finding (hollow tests for the destructive commands this repo actually runs) rather than an allocation criticism. The consequences are already visible: deployment, CI and release all still live in the legacy world (CI references pre-reorganization paths and provides no gate at all; release.yml depends on packaging scripts deleted by architectural decision; the production image builds FROM an undefined cbrowser:latest; the shipped artifact per CHANGELOG is upstream 0.1.8 plus an i18n toggle), the default install is unauthenticated on 0.0.0.0, and the project maintains two backends, two databases and two frontends indefinitely. Verdict: the target is defensible but over-sized for the demonstrated deployment envelope, and execution sequencing is clearly off — the highest-leverage strategic move is not more v2 or more tooling, but forcing the closing chain (fix the delivery pipelines, run the narrowed acceptance, migrate, delete legacy) so the differentiating architecture becomes the thing that actually ships. Follow-up adjudication resolved both open conditions: q_strategy_01 was confirmed in the negative — no remote/multi-user/multi-host goal exists anywhere in the record and the opposite is explicitly recorded (plan header, blueprint, decisions.md, handoff), so the fit judgment stands unsoftened; q_strategy_02 confirmed repo_template is a deliberate cross-repo platform investment consumed (not authored) by this repo, which withdrew the tooling-allocation criticism while leaving the consumption-side test-gap component standing; and q_strategy_03 refuted a data-preservation blocker behind t010/t011 — they are simply unstarted behind the unexecuted t009 — so f_global_strategy_01 stands as a sequencing failure, not a risk-constrained one.

- [High][80] docs/v2_architecture_plan.md; AGENTS.md:1-3; docs/tasks/t009_v2_full_acceptance/task.md:29,44 — Architecture is sized for multi-host streaming, but the demonstrated deployment premise is single-user, single-machine, same-host access
  - ID: f_global_strategy_02; verification: static
  - Evidence: AGENTS.md defines the product as a '单机 Docker 管理系统' (single-machine Docker management system); t009's test strategy deploys on the owner's Mac/OrbStack with same-host Chrome; archived t001 records the user decision '最终在当前电脑 Docker 部署、同机 Chrome 访问'; The v2 topology nonetheless comprises five resident services (Caddy, API, Supervisor, Stream Gateway, coturn) plus a Browser/Stream container pair per profile, TURN REST credentials with 24h lifetime / 12h rotation / ICE-restart lead time, and supervisor reconciliation — machinery whose payoff is NAT traversal, multi-host media relay and concurrent remote viewers; The capabilities that justify that machinery are the ones already waived: t009 AC-005 records public/NAT penetration as NOT_RUN/USER_WAIVED and native Linux x86_64 validation likewise; the gateway's RTC rotation-timing parameters exist to serve relay scenarios the deployment never exercises; On 2026-11-02 the user further narrowed t009 AC-003 from 1000-run automated input/clipboard pressure testing to a manual checklist, explicitly because it is single-person use ('单人使用') — the requirements envelope keeps shrinking toward 'local tool' while the architecture stays at 'service'
  - Impact: Complexity is not free: the multi-service topology is the direct source of whole classes of findings in this review (gateway heartbeat wedging, ICE restart_pending deadlock, fixture/production topology divergence, silent-green E2E layers that need five images to run). If the real envelope is one user on one machine, a large share of that risk surface buys nothing; if the envelope later grows, the waived validations (public ICE, 8h soak, capacity) will have to be re-bought at full price anyway.
  - Fix: Re-baseline the plan against an explicitly recorded deployment envelope. If single-machine/single-user is the durable premise, formally descope or park the multi-host-only machinery (public TURN/relay paths, credential rotation cadence) and simplify the topology targets for t012; if remote/multi-host use is a real goal, record it as a requirement with an owner and stop waiving its validations. Either answer is legitimate — the current state, full-size architecture plus waived justification, is the worst combination.

- [Low][85] .repo_template/ (1.4M); docs/ (5.4M) vs src/ (2.2M); _meta/unit_plan.json unit sizes — The consumed repo_template toolchain's riskiest surface is its least-tested — CBrowser runs destructive commands whose safety nets are hollow (the platform investment itself is external, per q_strategy_02)
  - ID: f_global_strategy_03; verification: static
  - Evidence: Unit sizes from the review inventory: template_scripts_state 10,471 lines + template_scripts_ops 3,838 + template_tests 11,580 + template_support 1,784 ≈ 27.7k lines of toolchain code and tests, versus ≈ 26.6k lines for the entire v2+legacy product backend (supervisor 6,458 + stream/gateway 5,647 + runtime/adapters 5,050 + api/auth 3,732 + core 5,732); On disk, docs/ (5.4MB, including task ledgers, findings, archives) is roughly 2.5x src/ (2.2MB); .repo_template/ alone is 1.4MB; The toolchain's destructive commands are exactly where its tests are hollow: purge's refusal guards are all stubbed to permissive in tests, one drop test never invokes cmd_drop and asserts an either-way outcome, and fixtures fabricate 'verdict: PASS' review evidence while disabling all project gates (template_tests Medium/Low findings); The toolchain also produced this review's only tooling High outside product code: the task ledger reads fail-open on OSError, silently restarting attempt numbering — the opposite of its own fail-closed invariant (template_scripts_state f_01); Follow-up q_strategy_02 (confirmed): AGENTS.md:12 declares CBrowser a template consumer ('本项目使用模板仓 repo_template…消费仓不得删除'); the entire .repo_template tree entered in a single import commit 524e34e (2026-10-26) and no later commit in the 265-commit history touches it; .repo_template/docs/usage.md documents a producer/consumer sync protocol and archive notes record pending upstream template differences not yet pulled — the toolchain is authored and maintained outside this product, so its line count is not this product's effort allocation
  - Impact: The allocation criticism originally attached to this finding is withdrawn: the toolchain's ~27.7k lines are not this product's investment — q_strategy_02 confirmed the template is authored and maintained in its own repo, imported wholesale and never edited in this repo's history, so its budget belongs to the platform portfolio, not to CBrowser. What remains chargeable to CBrowser is consumption risk: this repo actually executes the toolchain's destructive commands (purge, drop, sync, cleanup) against its own work, and in the consumed copy those are precisely the operations with hollow tests (purge guards stubbed permissive, a drop test that never invokes cmd_drop, fixtures fabricating PASS review evidence) plus a fail-open task ledger that restarts attempt numbering on read errors (template_scripts_state f_01, High). CBrowser also committed no sync_manifest.json baseline, so a fresh clone cannot tell which template version it is running (follow-up f_followup_q_strategy_02_01, Low). The risk is bounded — defects can be reported upstream via the template-issue-report channel instead of fixed locally, per AGENTS.md discipline — but until the consumed copy is hardened, every destructive run here carries it.
  - Fix: Do not charge or cap this as product effort; the platform budget is judged at the template repo. For CBrowser: (1) run one formal repo_sync cycle and commit the resulting .repo_template/sync_manifest.json so the consumed template version is recorded in-repo (follow-up f_followup_q_strategy_02_01); (2) report the destructive-command test gaps and the ledger fail-open defect upstream via the template-issue-report channel, and treat local purge/drop/sync/cleanup runs as un-netted operations (dry-run / explicit manual review) until the consumed version includes the hardening; (3) keep this repo's own priority on the closing chain (t009–t012, f_global_strategy_01).

- [Medium][90] CHANGELOG.md; README.md (快速上手); compose.yaml:10-17 — The fork's differentiation is unshipped: what a user gets today is upstream's app, rebranded, with a default-open security posture
  - ID: f_global_strategy_04; verification: static
  - Evidence: CHANGELOG's latest entry is 0.1.9 (2026-10-16): 'Based on upstream CloakBrowser Manager 0.1.8, rebranded to CBrowser' plus an EN/中文 UI toggle — the entire v2 rebuild has no changelog presence; README's quickstart (docker compose up, http://localhost:56661) installs the legacy single-container stack; nothing in the documented path reaches the v2 topology that constitutes the fork's stated reason to exist ('在架构上彻底重构为独立 Docker 容器沙箱与 WebRTC 架构', AGENTS.md); That shipped default is the weakest artifact in the repo: AUTH_TOKEN blank means auth middleware disabled, published on 0.0.0.0:56661, exposing profile cookies/files and /api/shutdown + /api/open-external to the LAN (f_contracts_deploy High), plus clipboard contents written to logs (f_backend_core_02 High)
  - Impact: Strategically the fork currently has the worst of both worlds: it has diverged from upstream (so upstream fixes don't flow in cleanly) while shipping none of its own improvements. The longer t011/t012 wait, the more the public artifact defines the project's reputation.
  - Fix: Independent of the t010 migration timeline, harden the shipped default now (fail-closed when AUTH_TOKEN is unset on a non-loopback bind, or bind loopback by default) and make README/CHANGELOG state plainly that the Docker quickstart is the legacy stack while v2 is pre-release. - [Medium][95] .github/workflows/ci.yml; .github/workflows/release.yml; config/docker/Dockerfile:1-2 — There is currently no working delivery mechanism for either stack — a cheap, blocking gap that outranks most feature work
  - ID: f_global_strategy_05; verification: static
  - Evidence: ci.yml's two jobs reference pre-reorganization paths (backend/, frontend/, frontend/package-lock.json) that no longer exist, and cover none of the root pyproject's three testpaths — the repository effectively has no CI gate (f_repo_ops_01, High; independently confirmed from the frontend build-wiring side); release.yml's native-package jobs invoke packaging/ scripts that were deleted by architectural decision, and its release job depends on them, so no v* tag can produce a Release; its Docker jobs omit 'file:' and default to a root Dockerfile that does not exist (f_repo_ops_02/03, High); The production Dockerfile builds FROM cbrowser:latest — an image defined nowhere in the repo, unpinned, with the build output tagged with the same name, so a clean machine either fails or silently builds on a stale same-named image (contracts_deploy High)
  - Impact: Every other strategic goal — shipping v2, hardening the legacy default, trusting the large test suite — is gated on pipelines that mechanically cannot run. The silent-green E2E pattern (tests_e2e_supervisor/tests_e2e_stream_frontend Highs) is partly a downstream symptom: CI never supplies the image env vars, so whole layers skip. Until this is fixed, 'tests pass' and 'release works' are unverifiable claims, and the project's substantial genuine test investment yields no signal.
  - Fix: Promote pipeline repair to the front of the queue, ahead of t009: point ci.yml at src/backend, src/frontend and all three testpaths; delete or repair the packaging-dependent release jobs; set the Docker build file explicitly; replace FROM cbrowser:latest with a defined, pinned base. This is days of work that unblocks the entire closing chain.
