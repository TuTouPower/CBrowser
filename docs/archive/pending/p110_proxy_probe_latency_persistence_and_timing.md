# p110 代理测速结果与可用性仅存前端临时态致刷新丢失，且端到端测量含 Docker 建毁开销致延迟高达 1759ms

- 现象：1）代理列表点击单条/全部测速后展示的延迟毫秒数与“可用/测速失败”状态仅存在当前组件内存中，刷新页面或切换路由后完全丢失，且当后端探测失败并返回 HTTP 200（`observation_status: "failed"`）时前端仍误判为“可用”并弹出成功提示；2）测速显示高达 `1759ms` 等秒级异常延迟，远超真实代理链路耗时。
- 影响：影响全部代理测速交互、跨刷新/跨页面状态一致性以及用户对代理质量的判断，包括：1）`ProxyListPage` 列表视图（`ProxyTable`）与卡片视图的可用状态与延迟展示（卡片视图还完全漏渲染 `failed` 徽章）；2）`ProxyFormDialog` 编辑弹窗与 `SessionDetailsPanel` 会话详情仅消费 `observation_status === "pending"` 与 `country_code`，无法区分 `failed` 与 `unknown` 且无延迟可展示；3）`handleProbe` 与 `handleProbeAll` 均存在同源计时失真与忽略 `observation_status` 的问题（`handleProbeAll` 还串行触发逐个容器重建，批量耗时线性放大）。
- 根因：属产品架构与前后端契约缺口（产品缺陷）：
    1. **状态与延迟未纳入后端持久化与响应契约**：`ProxyEgressObservationModel`（`src/backend/cbrowser/adapters/database/models.py`、`migrations/versions/0006_proxy_egress_observations.py`）、`EgressObservation`（`domain/egress_observation.py`）、`EgressProbeResponse`（`supervisor/protocol.py`）、`EgressProbeResult`（`services/egress_probe.py`）与 `ProxyResponse`（`domain/models.py`）仅持久化和返回 `egress_ip`、`country_code`、`observation_status`（`unknown`/`pending`/`ok`/`failed`）与 `observed_at`（库表仅另存未暴露的 `error_code`），全链路无 `latency_ms` 字段。
    2. **前端将测速结果放在组件局部 `useState` 且忽略 `observation_status`**：`ProxyListPage.tsx` 使用组件内 `useState`（`speedResults`）保存状态与毫秒数，卸载/刷新即清空；`useProbeProxyMutation`（`useProfilesQuery.ts`）仅作用于列表缓存失效，不承载延迟；`ProxyTable.tsx` 与 `ProxyListPage.tsx` 卡片视图仅在 `observation_status === "pending"` 时读取后端状态，未从 `ProxyResponse` 渲染 `ok`/`failed`；且 `ProfileService.probe_proxy_egress` / `POST /api/v1/proxies/{id}/probe` 在探测失败时写入 `failed` 观测并返回 **HTTP 200**，而 `handleProbe`（`onSuccess`）与 `handleProbeAll`（`mutateAsync` 后）均未检查返回的 `observation_status`，一概按成功记入 `{ status: "ok", ms }` 并 toast `proxyProbeSuccess`。
    3. **测量口径把整个 Docker 容器与外部 HTTPS 探测生命周期算作代理延迟**：`ProxyListPage.tsx` 在 `handleProbe` / `handleProbeAll` 中用 `Math.max(12, Date.now() - startedAt)` 测量整个 HTTP `POST /api/v1/proxies/{id}/probe` 耗时；后端 `DockerAdapter.run_egress_probe`（`src/backend/cbrowser/supervisor/docker_adapter.py`）每次测速同步执行「新建临时 bridge 网络 → 创建并启动睡眠 `browser_image` 容器 → `exec_run` Python `getaddrinfo` → 创建/启动/等待/删除 `policy_image` 容器安装 iptables 规则 → `exec_run` Python 冷启动运行 `cbrowser.runtime_agent.egress_probe` → `finally` 同步强删容器与网络」（本机实测仅容器/网络/策略/Python 冷启动与清理即达 **5579.66 ms**），叠加 `shared/egress.py` 中 `ECHO_URLS`（3 个外部 HTTPS 服务，单跳 `timeout=10.0`、无连接复用、含 TLS 建连与串行回退）与 API/Supervisor/SQLite 往返，直接导致页面显示 `1759ms` 等秒级假延迟。附带同类位点扫描：`src/frontend/src/` 内仅 `ProxyListPage.tsx` 的 `handleProbe` 与 `handleProbeAll` 存在 `Date.now() - startedAt` 测速误用；`ProxyListPage.tsx` 卡片视图（漏 `failed` 徽章）、`ProxyFormDialog.tsx` 与 `SessionDetailsPanel.tsx` 存在同类仅认 `pending` 不认 `failed` 的状态展示缺口；另核查 `docker_adapter.py:_exec_probe_helper` 与 `runtime_agent/egress_probe.py` 发现：后者发生 `EgressProbeError` 时输出 `{"error_code": ...}` 并以退出码 `1` 退出，前者因 `exit_code != 0` 直接抛 `DockerSandboxError` 跳过 `_parse_probe_output`，导致特定失败码退化为通用 `probe_failed`。
    4. **与 `p040` 的关系（未改动 `docs/pending/parked/p040_proxy_connectivity_exit_ip_check.md`）**：`p040` 原包含“连通性检测（握手成功与否、延迟）”与“出口 IP / 地理位置”，`t052` 仅落地了出口 IP 与 GeoLite2 国家观测，`p040` 中“连通性与延迟检测”继续暂搁；此后前端在未补齐后端延迟测量与状态契约的情况下，直接给 `t052` 出口探测接口套了 `speedResults` 与 `Date.now()` 壳作为“闪电测速”，诱发本缺陷。修复需决定是否重新激活 `p040` 的服务端握手/延迟测量与观测持久化（或将轻量连通性测速与重型容器出口 IP 校验解耦）。
- 测试缺口：1）前端 `src/frontend/src/features/proxies/ProxyListPage.test.tsx` 中 `probe` mock 立即返回 `observation_status: "ok"`，未测组件卸载重挂（刷新）后持久化状态与延迟保持、未测 `probe` HTTP 200 返回 `observation_status: "failed"` 时 UI 误判为可用的回归、未测卡片视图 `failed` 展示、也未断言延迟来自服务端观测字段而非客户端计时；2）后端 `tests/unit/test_t052_supervisor_probe.py` 使用 `_FakeDockerClient` 零延迟替身（且 `_FakeContainer` 对 `error_code` 返回 `exit_code=0`，掩盖了真实 `egress_probe.py` 返回 `1` 的路径），`test_t052_observation_repository.py` 与 `tests/integration/test_t052_proxy_api.py` 仅校验 `egress_ip`/`country_code`/`observed_at`；应在后端补齐观测表/响应的延迟字段单测与集成测试（及真实 `exit_code=1` 解析测试），并在前端补齐刷新重挂持久化、HTTP 200 `failed` 状态处理与列表/卡片视图一致性的测试断言。
