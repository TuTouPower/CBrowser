# p068 登录页 500：SQLite WAL 落 macOS 宿主 bind mount，-shm mmap 失稳

- 现象：2026-11-10 18:37:21–18:51:44（CST）期间点击「解锁」后登录页直接显示 `A database error occurred`；同一窗口 `/api/v1/auth/session` 也 500。18:51:45 自行恢复，18:56 登录成功，API 容器全程未重启（`RestartCount=0`）。截图为该 500 的前端展示。
- 影响：登录与既有会话校验在数据库瞬时故障时完全不可用；前端只拿到英文原文，绕过 i18n。`cbrowser-api` 日志 966 行 `disk I/O error`、322 次 `Database error: OperationalError (disk I/O error)`，涉及 300 次 `profile_runtimes` 读、19 次 `sessions` 读、3 次 `sessions` 过期删除（登录建会话），说明密码校验已通过、失败发生在建会话写入。故障不是全局停机：同一窗口 `/internal/supervisor/profiles` 列表 841 次全 200，`{id}/runtime` 627 次 200 与 242 次 500 交错；`data/v2/profiles/.../TransportSecurity`（18:37:58）和 `DIPS-wal`（18:46:49）仍被浏览器容器正常写入，说明宿主共享目录整体可写，问题集中在 SQLite 的长连接与 mmap 句柄。数据库副本 `PRAGMA integrity_check` 为 `ok`。
- 根因：已定位为 SQLite WAL 与 macOS↔OrbStack VM 的宿主 bind mount 不兼容。业务库位于 `data/v2/cbrowser.db`（`compose.yaml` 将 `${CBROWSER_DATA_ROOT}:/data` 从 macOS 挂入 VM），WAL 需要把 `-shm`（wal-index）用 `mmap` 映射并在进程间共享；该文件跨宿主/VM 边界时 mmap 一致性与锁语义不可靠，SQLite 会返回 `SQLITE_IOERR`（缺省文案即 `disk I/O error`），表现为按页/按帧间歇失败、连接不重建就持续报错，直到 shm 映射重建后自愈。SQLite 官方 WAL 文档明确要求所有进程同机共享内存；OrbStack 也曾在 v1.10.0 修过 “occasional SQLite I/O errors on bind mounts”，说明这是该挂载方式的固有风险，单用户、低并发同样会中招，与性能/负载无关。当前 OrbStack 2.2.3。应用层还放大了故障：`src/backend/cbrowser/api/app.py:391` 的 `DBAPIError` 处理器把除 `IntegrityError` 外的异常一律映射为 500 `database_error` / `retryable=false`；`AuthService` 全部方法（`has_admin`、`authenticate_admin`、`create_session`、`get_valid_session`、`revoke_session`、automation token 系列）直接使用 `session_maker`，没有 `DBAPIError` 分类；`ProfileService._handle_db_error`（`src/backend/cbrowser/services/profile_service.py:334`）只把 `SQLITE_BUSY`/`SQLITE_LOCKED` 转成可重试 `DatabaseLockError`，`SQLITE_IOERR` 落回通用 500。已扫同类位点：`AuthService` 全部方法、`ControlService`、`NetworkService`、`ArtifactService/ArtifactRepository`；前端 `LoginPage.tsx` 仅透传 `err.message`，无错误码映射与重试。
- 测试缺口：现有 `test_a6_error_contract.py` 只断言 HTTPException 与 500 结构，`test_auth_service.py` 不注入 `OperationalError`；没有“认证/控制/网络接口遇 `SQLITE_IOERR` 应有确定降级或有限重试”的测试，也没有“登录失败错误码映射到 i18n 文案”的前端测试。应在 unit 层用可注入的 `OperationalError("disk I/O error")` 断言分类/重试边界，在 integration 层断言登录在建会话瞬时失败后可恢复，并补前端错误码到文案的断言。存储侧需补“数据库不位于宿主 bind mount”的部署断言（compose 结构测试）。
- 线索：`.scratch/repro_login_disk_io_error.py` 以桩 AuthService 抛 `sqlalchemy.exc.OperationalError(..., sqlite3.OperationalError("disk I/O error"))`，复现返回 `500 {"error":"database_error","message":"A database error occurred","retryable":false}`。事故原始证据：`docker logs cbrowser-api -t`（`ERROR [cbrowser.api] Database error: OperationalError (disk I/O error)`，10:37:23Z–10:51:44Z）、`docker logs cbrowser-supervisor -t`（同步 `api_status=500`）、`docker logs cbrowser-api -t` 中同窗口 200/500 交错统计、`stat` 浏览器 profile 文件在故障窗口内的成功写入。日志缺口（尚无法证明是 `IOERR_SHMMAP` 还是 `IOERR_READ/WRITE`）：`app.py` 只记录 `type(exc).__name__` 与 `str(exc.orig)`，未记录 `sqlite_errorcode`/`sqlite_errorname`、请求路径、故障时 db/wal/shm 的 `stat`（inode/size/mtime），也未记录首次恢复成功；需补这些字段后再复现或下一次故障时定死扩展错误码。
