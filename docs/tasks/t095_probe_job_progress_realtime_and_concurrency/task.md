# Task spec

## 背景

t094 上线后生产批量测速暴露三个症状：进度条长期显示「0/88」但列表已出结果、行状态不随探测推进、88 个代理跑完要数分钟。生产作业 `049e0ef6` 实证：`total=88, completed=0, failed=50`，已处理过半但进度为零；成员严格串行、失败吃满 10 秒超时。

按开发铁律（架构至上、拒绝妥协、零兼容负担）分析，三个症状同源，根因在领域模型与状态管道：

- 进度被建模成「成功数」而非「已处理量（成功+失败）」，失败这一正常终态被排除在进度外，失败场景必然长期归零。
- 作业驱动单成员串行、单探测超时彼此阻塞，整体耗时随代理数线性放大。
- 状态的生产、聚合、分发是三条独立路径：观测落库不推送、列表不刷新、进度只读作业计数；观测表还承担「推断当前状态」职责，与作业状态双轨并存。

本 task 从根因重做，不改文案、不加轮询补丁。

## 契约区

### 范围

- 进度与结果正交：作业读模型的进度为「已处理数 = 成功 + 失败」，终态汇总分别呈现成功数与失败数；单条与批量、代理测速与环境批量三动作的进度语义统一。
- 受配额并发执行：作业驱动在服务端并发上限内并行探测，单成员超时彼此独立；并发上限可配置，超限有明确拒绝/排队语义；整体耗时不再随代理数线性放大。
- 统一状态管道：成员状态每次迁移即发出进度事件，一次推送同时驱动进度读模型与代理列表刷新；观测写入后列表逐条实时更新，不靠固定间隔轮询。
- 观测表职责归位：只存单次探测结果记录；作业进度以作业读模型为唯一权威，不从观测表反推当前状态或进度；历史观测保留且仍按有效期判定。
- 前端进度展示：运行中显示「已处理/总数」，终态显示成功/部分失败/全失败汇总；行状态由服务端推送的事件驱动刷新。
- 同步 OpenAPI 契约、生成类型、blueprint/spec 文档与相关测试。

### 非范围

- 不排查代理本身为何大量失败（另由独立子代理研究 mihomo proxy，不属本 task）。
- 不改变探测协议支持范围（http/https/socks5 保持）、白名单回显、本地 GeoIP 与防泄露边界。
- 不在生产环境做破坏性验证；生产发布另行授权。
