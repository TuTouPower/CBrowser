## 数据完整性与证据边界

- `profiles.list` / `proxies.list` / `groups.list` 前端无分页参数，后端 repository 当前用 `.all()` 返回全量，本轮未发现“只拉前 N 条却宣称全量”的截断机制。无分页不等于已完成规模适配。
- 列表页搜索过滤在全量数据上执行；后续若选择分页、虚拟列表或按需加载，须同时明确全局搜索、全选、计数和筛选范围，不能让界面只在可见页搜索却暗示搜索全部。
- 本轮真实浏览器探针为生产组件加 mock 数据，Select 为 200 候选，其他浮层为 100 环境/100 分组；SQL 在 `.scratch/` 临时 SQLite 运行。没有创建真实环境、修改代理或执行删除/迁移。
- 1000 条以上交互容量、内存、首屏/搜索耗时尚未压测，不承诺所有场景已通过。没有虚拟列表/没有分页本身不直接定为 bug，不预先指定技术方案。

## 实施验收方向

1. 建立覆盖 0、1、少量、100、1000 条的环境/代理/分组 mock 数据矩阵；这些是验证样本，不冒充产品支持上限，必要时明确实际目标规模与性能预算。
2. 真实浏览器覆盖普通窗口、窄窗口、低高度、缩放、中英界面及长名称；对所有可增长候选验证列表具有有效滚动范围、容器留在可用视口、末项鼠标/键盘可达与可选，背景不被误滚。
3. 大量代理/分组等可增长选择提供直接搜索定位，保留直连/无分组/全部等特殊项与当前选中值。搜索不应只覆盖已渲染的一小段。
4. 验证全量数据完整性、筛选/排序、列表与卡片一致性、计数与明细一致、批量操作范围和失败保留；不可只断言 CSS 含 overflow 类。
5. 记录目标规模下首屏、搜索/筛选、切换、打开下拉、网络与 SQL 数量；复用已有能力，以测量结果选择最简方案，不为未经测量的性能风险直接引入复杂架构。
6. 测试必须触达生产组件/查询逻辑；当前多数 jsdom 测试只用少量 fixture，无法判断真实几何与滚轮可达性，应补生产组件真实浏览器规模回归。
