# p125 Supervisor 字体集挂载误传容器内路径导致浏览器零字体、页面崩溃与文字不可见

- 来源：2026-11-17 用户反馈与现场截图（空白/崩溃页、`baidu.com` 仅见图片与色条但全部文字消失、输入字母看不到）；`/bug-to-pending` 调查与最小复现。
- 现象：通过 `compose.yaml` 部署的堆栈启动绑定了平台字体集的环境（`0022`/`0023`/`0024`/`0026` 均复现）后：1) 浏览器访问 `chrome://settings/searchEngines` 等页面或部分标签直接白屏并出现 Chromium 崩溃图标（“Aw, Snap!”），`search_defaults_status.json` 报错 `ProfileDefaultsError`（`TargetClosedError`）；2) 浏览器全部 UI 文字（标签页标题、地址栏、补全列表、崩溃页提示与按钮）及网页系统字体文字完全不显示，仅图片、SVG 和纯色块可见；3) 键盘输入实际已送达浏览器（`0024` 的 CDP 目标列表存在用户键入的 `chrome://123asdfasdfasdf/`，`0026` 的 X11 截图显示地址栏下拉已弹出、Stream 日志记录 `input=True`），但因零字体无法成形，在用户视角表现为“一片白、无法输入字母、像是文字颜色变成了白色”。
- 影响：所有使用 `compose.yaml` 部署并绑定任意 `font_set_id`（`windows`/`macos`）的 Profile 均完全不可用；宿主机虽存在完整的 144 个 Windows 字体文件（`data/fonts/windows/71e2df2b...`），但所有运行中的 Browser 容器内 `FONTCONFIG_FILE=/run/cbrowser/runtime/profile-fonts.conf` 下 `fc-list` 均为 0 条字体，且 `agent` 的 `/health` 仍返回 `status="ok"`、`ready=true`。
- 根因：部署配置与产品缺陷叠加（宿主机路径 vs 容器内路径混用，叠加运行时缺少非空字体集 fail-closed 门禁，并被现有规范与测试假绿固化）：
    1. **宿主机与容器内字体路径混用（主因）**：`compose.yaml:141,150` 将宿主机 `${CBROWSER_FONTS_DIR}` 挂载到 `supervisor` 容器内的 `/fonts:ro` 并设置 `CBROWSER_FONTS_DIR: /fonts`（不同于同服务下 `CBROWSER_DATA_ROOT` 与 `CBROWSER_SOCKET_ROOT` 的同路径挂载 `${VAR}:${VAR}`）。`DockerAdapter.start_browser_container`（`src/backend/cbrowser/supervisor/docker_adapter.py:1939-1950`）通过宿主机 Docker socket 创建 Browser 容器时，直接把 `os.environ.get("CBROWSER_FONTS_DIR")`（容器内路径 `/fonts`）拼接成 `host_font_dir = /fonts/<platform>/<font_set_id>` 作为宿主机 bind source 传给 Docker daemon。因宿主机/OrbStack VM 根目录下并不存在 `/fonts/...`，Docker daemon 自动在 VM 内创建空目录并只读挂入 Browser 容器的 `/run/cbrowser/fonts/<platform>/<font_set_id>`。
    2. **启动与健康检查未对绑定字体集空目录 fail-closed**：`SupervisorCore._validate_font_set`（`src/backend/cbrowser/supervisor/core.py:2609-2636`）在 Supervisor 容器视角检查 `/fonts/<platform>/<font_set_id>`（存在且校验通过），无法发现传给 Docker daemon 的 bind source 与自身挂载路径不一致；而 Browser 容器内的 `BrowserRunner.start`（`src/backend/cbrowser/runtime_agent/runner.py:525-547`）与 `fontconfig.py:73-155` 仅根据 `cfg.font_set_id` 拼接 XML `<dir>` 路径，未校验挂载点是否真实可读、非空或包含有效字体集（`manifest.json` / 字体文件 / `fc-list`），导致容器在 0 字体状态下仍写出 `profile-fonts.conf`、拉起 Chromium 并上报 `running`。Chromium 随后因 `fc-list` 为空在渲染进程命中 `FATAL:third_party/skia/src/ports/SkFontMgr_FontConfigInterface.cpp:163] Not implemented` 崩溃（`.dmp` 转储），并在 UI 文本成形路径命中 `ui/gfx/render_text_harfbuzz.cc:1129: NOTREACHED hit. The glyph range is empty or invalid! ... glyph range: [0, 0]` 与 `remote_font_face_source.cc:365`，使全部文字隐身。`agent.py:185-224` 虽在 `missing_fonts` 列出全部 17 个检测字体缺失，`/health` 仍返回 `ready=true`。
    3. **补充说明（非本 bug，避免误判）**：用户首张截图左上角的深灰 `1.00` 角标为宿主机浏览器倍速扩展覆盖在 `<video>` 上的元素，左侧粉色竖条为 Selkies 官方侧边栏折叠手柄 `.toggle-indicator`（`--sk-accent:#ec4899`）；`en-US` 下 `fontconfig.py` 主动 reject `zh*` 字体的策略已有 `p116` 独立追踪，不归为本次无字体故障。
- 同类扫描：已逐项核查 `compose.yaml` 全部服务及 `src/backend/cbrowser/supervisor/` 全部环境变量与 Docker `volumes` 构造位点：
    - `compose.yaml` 中 `supervisor` 其余需要经 `docker.sock` 透传给宿主机 daemon 的变量（`CBROWSER_DATA_ROOT`、`CBROWSER_ENGINE_CACHE`、`CBROWSER_GEOIP_CACHE`、`CBROWSER_SOCKET_ROOT`）均已使用 `${VAR}:${VAR}` 同路径映射；`docker_adapter.py` 中其余挂载（`browser_volumes`、`stream_volumes`、`cache_init_volumes`、`probe` 与 `x11` helper）均源自上述同路径根。`api` 服务不持有 Docker socket，其 `CBROWSER_FONTS_DIR: /fonts` 仅作容器内读取，无同源故障。
    - 确认纳入同一修复范围的关联位点：`compose.yaml:141,150`、`src/backend/cbrowser/supervisor/docker_adapter.py:1939-1950`、`src/backend/cbrowser/runtime_agent/fontconfig.py` 与 `runner.py:525-547`（绑定 `font_set_id` 时的容器内字体目录/非空字体校验 fail-closed）、`src/backend/cbrowser/runtime_agent/agent.py`（字体集缺失时健康状态边界）、`docs/specs/release_deployment.md:55` 及 `tests/unit/test_t027_release_controller.py:1181-1184`（见测试缺口）。
- 测试缺口：
    1. **旧测试固化了缺陷**：`tests/unit/test_t027_release_controller.py:1168-1185` 直接断言 `supervisor` 服务必须具备 `CBROWSER_FONTS_DIR: /fonts` 与 `${CBROWSER_FONTS_DIR}:/fonts:ro`，将宿主/容器路径分裂写入测试契约（修复时须按 TDD 规则整体替换该旧断言并说明裁决来源）。
    2. **单测与门禁环境屏蔽了分裂路径**：`tests/unit/test_t041_font_runtime.py:137-155` 在宿主机进程内用 `tmp_path` + `MagicMock` 测 `DockerAdapter`，测试中 `CBROWSER_FONTS_DIR` 既是进程内读取目录又是 Docker bind source，无法暴露容器化 Supervisor 下的路径分裂；`scripts/run_gates.sh:259-264` 全程 `unset CBROWSER_FONTS_DIR`，使全栈 E2E（`test_frontend_app_e2e.py` 等）始终只跑 `font_set_id=None` 的镜像内置基础字体回退分支，从未覆盖“容器化 Supervisor + 绑定 `font_set_id` + 真实 Browser 容器”链路。
    3. **应补测试**：(a) 契约/配置单测：`compose.yaml` 中 `supervisor` 的字体卷挂载与传给 `DockerAdapter` 的宿主机字体根目录必须能解析到宿主机真实目录（例如同路径挂载 `${CBROWSER_FONTS_DIR}:${CBROWSER_FONTS_DIR}:ro` 或显式分离 `CBROWSER_HOST_FONTS_DIR`）；(b) 单元/集成测试：模拟容器内 `CBROWSER_FONTS_DIR` 与宿主字体根不同（若仍允许分离）或校验 `DockerAdapter` 仅将宿主机根传给 `volumes`；(c) BrowserRunner/fontconfig 单测：绑定 `font_set_id` 但 `/run/cbrowser/fonts/<platform>/<id>` 为空目录/无字体/损坏 manifest 时，必须 fail-closed 抛出 `FontConfigUnavailableError`（`font_set_unavailable`）而不是带着 0 字体启动 Chrome；(d) 真实 Docker E2E：经容器化 Supervisor（按 `compose.yaml` 挂载方式）启动绑定 `windows` 字体集的真实 Browser 容器，断言容器内 `fc-list` 非空、`search_defaults` 为 `applied`、无渲染进程 crash dump，且地址栏/网页文字正常渲染、键盘字母可正常输入并显示。
- 线索：

    - `.scratch/bug_probe/repro.py`、`repro_result.json`、`repro_broken_empty_fonts.png`、`repro_fixed_real_fonts.png`：用现行 Browser 镜像 `sha256:ea67d5ed27b9` 对照“挂载空目录”与“挂载真实 `data/fonts/windows/71e2df2b...`”，前者复现 `fc-list=0`、3 个 `.dmp` 崩溃文件、`search_defaults=failed (ProfileDefaultsError)` 及地址栏输入 `https://example.invalid/abc` 后下拉框打开但全部字母不可见；后者 `fc-list=218`、`search_defaults=applied`、0 崩溃且全部文字正常渲染。
