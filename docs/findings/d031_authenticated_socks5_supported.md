# d031 Chromium 146 支持带认证 SOCKS5（t035 / s013）

- 来源：`docs/spikes/s013_authenticated_socks5_engine_probe/report.md` 正式 spike，2026-11-05 在 Linux arm64 探针容器内以真实引擎 `chromium-146.0.7680.177.3/chrome` 实测。
- 事实：`--proxy-server=socks5://user:pass@host:port` 时，引擎 greeting 只声明 RFC 1928 method `0x02`（用户名/密码认证），完成 RFC 1929 子协商；正确凭据 → 认证 accepted、页面经代理加载、HTTP 目标收到代理转发的请求；错误凭据 → 认证 rejected、`net::ERR_SOCKS_CONNECTION_FAILED`、页面加载失败、无请求到达目标。无认证对照（method `0x00`）亦正常。
- 结论：**CloakBrowser 0.6.4 / Chromium 146 支持带认证 SOCKS5**；契约背景「Chromium 原生不支持」的假设不成立。t035 AC-008 取「引擎支持时端到端经代理出站」分支，API 不以 422 拒绝 `socks5`+凭据组合；但凭据变更须按 `credential_revision` 失败封闭（AC-007）。`--proxy-bypass-list=<-loopback>` 仅为 spike 强制本地目标走代理，生产不需要。
- 复查条件：Chromium 主版本或 `fingerprint_platform` 升级后重跑 s013。
- 现状：有效（CloakBrowser 0.6.4 / Chromium 146 现行能力，ADR 023 依据）
- 采纳：t035（无后续 tid）。
- 现状补充：拆除外置认证转发器后，该能力成为 Browser 直连上游代理、凭据直接用于 `--proxy-server` 的依据（ADR 037）；`credential_revision` 失败封闭不变。
- 复核（2026-11-15 真 407 认证代理实测确认）：上轮「内联凭据只对 `socks5://` 成立、`http://` userinfo 不可用」结论方向成立，但机制归因修正并经严谨实验坐实。用真 407 认证代理（`Proxy-Authenticate: Basic realm="cbrowser-httpauth"`，校验 `base64(probeuser:probesecret)`，407/CONNECT/未知方法/转发/上游错误全分支打日志）+ Chromium 146（`chromium-146.0.7680.177.3/chrome`，镜像 `sha256:0de8e6e6dc8d15c0b3543501ef65e8056e95d5fb0a7b355c67437acfdd98eac0`）做 A/B/C 三组独立容器对照（`--dump-dom http://<target>:8080/`，目标 HTML 含唯一标记 `PROXY_OK_MARKER`）：A `http://probeuser:probesecret@<proxy>:18080`、C `http://probeuser:WRONG@<proxy>:18080` 的 proxy 日志仅 `PROXY_READY`、零 REQUEST/CONNECT，dump-dom 为 Chrome 错误页 `ERR_NO_SUPPORTED_PROXIES`、无 marker——带 userinfo 的 `http://` --proxy-server 不被解析为可用代理，连代理 TCP 都不发起，与密码对错无关；上轮「整段当主机名 DNS 失败」「加 407 亦不重试」均非 A 的真实原因（A 根本未连、未收到 407）。B `http://<proxy>:18080`（无凭据）为阳性对照：proxy 收到 `REQUEST ... proxy_auth=None` → `AUTH_CHALLENGE_407`（headless 无凭据故不再重试、不转发），证明代理与全量日志链路有效、去掉 userinfo 引擎即连代理。链路自检：正确 `Proxy-Authorization` 直连代理得 `AUTH_ACCEPTED`/`PROXY_GET`/`UPSTREAM_OK 200` 且含 marker，错/缺凭据均 407，证明「A 成功」判据可达、A 失败非装置缺陷。证据：`<home>/kar/code/CBrowser/.scratch/terminal_httpauth/`（`result.json`、`selfcheck.json`、`A|B|C_proxy_log.txt`、`A|B|C_chrome_stdout.txt`、`auth_proxy.py`、`target.py`、`run_experiment.py`、`selfcheck.py`）。产品结论不变：HTTP/HTTPS 带凭据上游不能依赖 URL userinfo；`build_proxy_server_arg` 现对此类配置 fail-closed 抛 `proxy_http_auth_unsupported`，需改用 `socks5` 或让上游免认证（见 `docs/specs/proxy_management.md`）。`tests/e2e/test_browser_runtime_e2e.py::test_t035_proxy_outbound_and_cdp_browser_version` 以无凭据配置验 egress，内联凭据 URL 拼装、编码与拒绝分支由 `tests/unit/test_t035_proxy_runtime.py` 覆盖。
